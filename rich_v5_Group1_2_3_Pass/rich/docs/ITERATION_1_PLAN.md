# 迭代1：8人分工、集成与验收建议

## 先确立一条原则

八个人不能各自编写八个带 `main()` 的独立程序。所有功能必须围绕同一份 `Game` 状态、同一个命令分发入口和同一套构建/测试命令开发。

## 推荐分工

| 人员 | 主要角色 | 第一轮责任 |
|---|---|---|
| 1（PO） | PO、A20开发、业务验收 | 澄清 Story；实现 A20；对照卡片验收；维护燃尽图 |
| 2 | 架构与集成人 | 维护 `Game` 公共结构、CMake、分支合并；禁止功能自行复制公共结构 |
| 3 | 功能开发 | A1 启动入口；只修改自己模块和必要接口 |
| 4 | 功能开发 | A2 玩家人数与角色选择 |
| 5 | 功能开发 | A3 初始资金设置 |
| 6 | 测试负责人 | 测试框架、测试命名、汇总执行命令；审查测试独立性 |
| 7 | 自动化测试 | 根据用例编写 A1/A2/A3 自动化测试，不参与对应功能实现 |
| 8 | 自动化测试与CI | 编写 A20 测试；配置 Windows/Linux/macOS 流水线；保存测试报告 |

人员2和人员6是合并时的双门禁：一个看代码结构，一个看测试结果。PO负责确认“做的是不是正确需求”，而不是代替开发人员判断代码细节。

## 各功能分支

- `feature/a1-startup`
- `feature/a2-player-selection`
- `feature/a3-initial-money`
- `feature/a20-quit`
- `test/a1-a3`
- `test/a20`
- `chore/ci`

禁止直接向 `main` 推送。每张 Story 使用一次 Pull Request；不要八个人在同一个分支连续覆盖文件。

## 合并顺序

1. 先合并项目骨架：公共头文件、CMake、空程序、空测试入口。
2. 测试组基于公共接口提交测试，允许此时测试失败，证明测试确实能发现未实现功能。
3. 分别合并 A1、A2、A3、A20；每次只合并一张 Story。
4. 每次合并后运行全部测试，不只运行该 Story 的测试。
5. 任一旧测试失败，立即停止后续合并，由引入失败的分支修复。
6. 全部绿色后打迭代标签，例如 `iteration-1-demo`。

推荐依赖顺序为：公共骨架 → A1 → A2 → A3 → A20。A20在架构上只依赖公共游戏状态和命令分发器，不应依赖地图、地产或破产模块。

## Pull Request验收门禁

每个 PR 必须同时满足：

- 对应 Story 编号和测试用例编号明确；
- 只包含本 Story 相关修改；
- C11 编译无警告；
- 新测试通过；
- 原有回归测试全部通过；
- Linux、Windows、macOS 三个平台流水线全部绿色；
- 测试失败时返回非0退出码；
- PO核对验收标准；
- 集成人检查没有重复的 `Game`、`Player`、`Map` 定义。

## 什么时候一张卡可以进入Done

“代码写完”不能进入 Done。必须满足：

1. 功能代码合入主干；
2. 自动化测试合入主干；
3. 测试与原电子用例能够对应；
4. 全平台流水线通过；
5. PO按验收标准演示通过；
6. README或接口说明已更新。

只有整张 Story 达到 Done 才从燃尽图中扣除其全部点数，中间完成百分比不扣点。
